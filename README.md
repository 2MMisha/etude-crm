# Etude CRM — etude-crm-app

CRM танцевальной студии на инфраструктуре GitHub: без сервера, без базы данных, без платного хостинга. Полная спецификация — в исходном ТЗ; этот README описывает архитектуру, как она реализована (упрощённый вариант с одним репозиторием данных — см. ниже).

## Архитектура

Два репозитория:

| Репозиторий | Видимость | Содержимое | Кто пишет |
|---|---|---|---|
| **`etude-crm-app`** (этот репозиторий) | публичный | код фронта, ничего больше | разработчик |
| `etude-crm-data` | приватный | все JSON-данные, включая посещаемость | приложение (от имени залогиненного пользователя) |

Этот репозиторий никогда не содержит реальных данных — только код. Он собирается Actions'ом (`.github/workflows/deploy.yml`) и публикуется на GitHub Pages по адресу `crm.ristar.co`.

### ⚠️ Модель авторизации — сознательный компромисс

В исходном ТЗ у каждого человека (админа и каждого преподавателя) был свой GitHub PAT, и это физически ограничивало доступ к деньгам: репозиторий с кассой был отдельным от репозитория с черновиками посещаемости. По решению владельца эта граница убрана в пользу простоты: **один общий GitHub-токен на весь `etude-crm-data`**, вшитый в сборку на этапе `npm run build` (`VITE_GITHUB_TOKEN`). Экран входа проверяет логин/пароль, но это **проверка только в интерфейсе**, а не настоящая граница безопасности:

- Токен присутствует в собранном JS-бандле, который отдаётся публично на `crm.ristar.co`.
- Любой, кто откроет DevTools (или просто посмотрит Network/Sources), может достать этот токен и получить полный `read/write` на `etude-crm-data` — включая кассу, зарплату и персональные данные учеников — независимо от того, что показывает интерфейс.
- Логин/пароль хранятся в `users.json` в виде `sha256(salt + пароль)` — это защищает от случайного просмотра файла, но не от целенаправленной атаки: у атакующего, доставшего токен, и так уже есть доступ к этому файлу.

Это принятое решение, а не недосмотр. Если для этой студии на каком-то этапе усилится порог риска (деньги, персональные данные детей — см. §8 ТЗ про требования израильского законодательства), правильный следующий шаг — маленький serverless-прокси (например, Cloudflare Worker бесплатного тарифа), который держит токен по-настоящему секретным и реально проверяет пароль на сервере перед тем как отдать доступ. Это уже обсуждалось и осознанно отложено.

## Стек

React 18 + Vite + TypeScript, TanStack Router (file-based routing, `src/routes/`) + TanStack Query, Tailwind, Dexie (офлайн-очередь, подключается в Фазе 2), Zod (`src/schemas/`), Vitest (`src/domain/*.test.ts`).

## Структура

```
src/
  schemas/    Zod-схемы всех сущностей — зеркало ТЗ §3, плюс user.ts (аккаунты)
  domain/     Бизнес-правила ТЗ §4 (баланс, начисления, скидки, зарплата) — чистые функции + тесты
  lib/github/ Contents API клиент с SHA-блокировкой (ТЗ §2.3) + config.ts (общий токен)
  lib/auth/   Логин/пароль, хеширование, локальная сессия, users.json
  routes/     Экраны — TanStack Router, файловая маршрутизация
```

## Разработка

```bash
npm install
npm run dev      # локальный сервер
npm run test      # Vitest — доменный слой
npm run build     # проверка типов + сборка
```

## Настройка окружения

Скопировать `.env.local.example` → `.env.local` (файл гитигнорится) и заполнить реальными значениями. Ничего из `.env.local` никогда не коммитится.

```
VITE_GITHUB_OWNER=2MMisha
VITE_DATA_REPO=etude-crm-data
VITE_GITHUB_TOKEN=<PAT с contents:read/write на etude-crm-data>
```

Для продакшен-сборки (`deploy.yml`) тот же токен кладётся как secret репозитория `etude-crm-app` под именем `DATA_REPO_TOKEN`.

## Ручной чек-лист: репозиторий данных

Эта часть требует доступа к GitHub-аккаунту и не автоматизирована здесь.

1. Создать приватный репозиторий `etude-crm-data`.
2. Создать один fine-grained PAT (от имени админа): `Repository access` → только `etude-crm-data`, `Contents: Read and write`, срок жизни 90 дней.
3. Положить этот токен в `.env.local` для локальной разработки и как secret `DATA_REPO_TOKEN` в настройках `etude-crm-app` (`Settings → Secrets and variables → Actions`) для продакшен-сборки.
4. Первый вход в приложение с любым логином/паролем создаст `users.json` и первого администратора — дальше новые аккаунты (в т.ч. для преподавателей) создаются на экране «Пользователи» (Фаза 1).
5. Отзыв доступа = замена или удаление токена (`DATA_REPO_TOKEN` и `.env.local`) — после этого нужна новая сборка/деплой, поскольку токен вшит в бандл на этапе сборки, а не читается динамически.

Дальнейшие шаги (схемы JSON в `etude-crm-data`, воркфлоу `validate`/`close-month`/`recalc-balances`/`backup`/`debtors`) — по мере прохождения Фаз 1–4, см. ТЗ §5, §7. Воркфлоу `merge-attendance` из исходного ТЗ не нужен в этом варианте — преподаватель пишет посещаемость напрямую в `etude-crm-data` через тот же Contents API.
